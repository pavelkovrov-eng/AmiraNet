# אפליקציית הכנה לבחינת אמירנט — מסמך עיצוב

**תאריך:** 2026-08-09
**מטרה:** ציון 134+ (רמת פטור) בבחינת אמירנט
**חלון זמן:** 6–12 שבועות מתאריך זה

---

## 1. הקשר ומטרה

בחינת אמירנט היא מבחן מיון אדפטיבי ממוחשב (CAT) של מאל"ו, המחליף את אמי"ר ואמיר"ם מאז מאי 2024. הציון נע בין 50 ל-150, וציון 134 ומעלה מקנה פטור מלא מקורסי רמה באנגלית באקדמיה הישראלית.

המשמעות הכלכלית של הפטור: חיסכון של עד חמישה קורסי רמה (800–2,000 ₪ כל אחד, ללא נקודות זכות), וסמסטרים של עיכוב בתואר.

המסמך מגדיר אפליקציית לימוד אישית, מקומית, שמטרתה היחידה היא להביא משתמש בודד לציון 134+.

### 1.1 ניתוח מבנה הבחינה

ששת פרקי הליבה, לפי מסמכי מאל"ו:

| פרק | סוג | שאלות | זמן |
|---|---|---|---|
| 1 | השלמת משפטים | 4 | 4 דק' |
| 2 | השלמת משפטים | 4 | 4 דק' |
| 3 | הבנת הנקרא | 5 | 15 דק' |
| 4 | ניסוח מחדש | 3 | 6 דק' |
| 5 | ניסוח מחדש | 3 | 6 דק' |
| 6 | השלמת משפטים | 4 | 4 דק' |

**סה"כ 23 שאלות מנוקדות, 39 דקות.** אחריהם 1–2 פרקי פיילוט (עד 2 נקודות בונוס, לא מורידים).

שתי מסקנות שמכתיבות את כל העיצוב:

1. **12 מתוך 23 שאלות (52%) הן השלמת משפטים — בדיקת אוצר מילים ישירה.** יתר סוגי השאלות תלויים באוצר מילים בעקיפין. אוצר המילים הוא המשתנה הדומיננטי, לא "טכניקות פתרון".

2. **הציון הוא פונקציה של קושי השאלות שנענו, לא של מספר התשובות הנכונות.** נבחן שעונה נכון על כל השאלות הקלות יסיים עם ציון נמוך מנבחן ששוגה בכמה שאלות קשות. **תרגול ברמה נוחה מייצר ציון נמוך.** האפליקציה חייבת לדחוף את המשתמש לרמת קושי גבוהה יותר מזו שנוחה לו.

## 3. הגישה שנבחרה

נשקלו שלוש גישות:

| גישה | תיאור | למה נדחתה |
|---|---|---|
| A — מכונת תרגול | מאגר גדול + תרגול מתוזמן + סימולציות | לא מטפל בשורש. קצב רכישת ידע נמוך: שעה = ~40 שאלות, מהן נלמדות בודדות מילים באקראי |
| **B — מנוע אוצר מילים מונחה-אבחון** | **SRS על AWL בליבה. שאלות הן יישום ומקור אבחון, לא המטרה** | **נבחרה** |
| C — סימולטור קודם | שחזור CAT מדויק, מבחנים מלאים, ניתוח שגיאות | 23 שאלות ל-39 דקות = קצב למידה גרוע. בלי מאגר ענק, שינון המבחנים תוך שבועיים |

**גישה B נבחרה.** A ו-C קיימות בתוכה כמצבי שימוש (תרגול חופשי, סימולציה שבועית), אך אינן הארכיטקטורה.

עקרון מנחה: **כל טעות היא נתון אבחוני, לא רק ציון.** האפליקציה מסווגת את *סיבת* הטעות ומזינה ממנה את תוכן הסשן הבא.

## 5. מודל נתונים

### 5.1 פריט לקסיקלי

```ts
interface Lexeme {
  id: string;                    // 'awl-analyze'
  family: string[];              // ['analyze','analysis','analytical','analytically']
  headword: string;
  definitionHe: string;
  definitionEn: string;
  pos: PartOfSpeech;
  morphology: {
    prefix?: string;
    root: string;
    suffixes: string[];
  };
  confusableWith: string[];      // מילים שמשמשות כמסיחים אמיתיים
  exampleSentence: string;
  difficulty: 1 | 2 | 3 | 4 | 5;
  tags: string[];                // 'awl-sublist-1' | 'connector-contrast' | ...
}
```

### 5.2 פריט שאלה

```ts
interface QuestionItem {
  id: string;                    // 'sc-0142'
  type: 'sentence-completion' | 'restatement' | 'reading' | 'grammar-in-context';
  difficulty: number;            // סולם theta, -3.0 עד +3.0
  stem: string;
  options: [string, string, string, string];
  correctIndex: 0 | 1 | 2 | 3;
  explanationPerOption: [string, string, string, string];
  targetLexemes: string[];       // מזהי Lexeme שהשאלה בודקת
  trapType: TrapType;
  passageId?: string;            // רק לשאלות הבנת הנקרא
}

type TrapType =
  | 'phonetic-neighbor'    // מסיח דומה בצליל/כתיב
  | 'logic-inversion'      // הפיכת סיבה/תוצאה או ניגוד
  | 'scope-shift'          // הוספה או השמטה של מידע
  | 'tense-shift'          // שינוי זמן דקדוקי
  | 'surface-match';       // חזרה על מילים מהמקור בלי שימור משמעות
```

**`targetLexemes` היא ההחלטה הנושאת של המסמך.** הקישור בין שאלה למילים שהיא בודקת הוא מה שמאפשר למנוע האבחון לומר "טעית כי אינך יודע `implicit`" במקום "טעית ב-14 שאלות". בלעדיו האפליקציה היא מכונת תרגול (גישה A).

`explanationPerOption` — הסבר לכל אחת מארבע האפשרויות, כולל השגויות. לדעת *למה* מסיח שגוי הוא מה שמונע נפילה חוזרת באותה מלכודת.

### 5.3 קטע קריאה

```ts
interface Passage {
  id: string;                    // 'psg-014'
  title: string;
  body: string;                  // מספר פסקאות, אנגלית
  domain: 'science' | 'history' | 'psychology' | 'economics' | 'humanities';
  difficulty: number;            // theta, -3.0 עד +3.0
  wordCount: number;
  questionIds: string[];         // חמש שאלות, לפי סדר הצגה
}
```

`difficulty` של הקטע נפרד מזה של השאלות עליו: קטע קשה יכול לשאת שאלה קלה ולהפך.

### 5.4 מצב משתמש

```ts
interface UserState {
  theta: number;                       // אומדן יכולת נוכחי
  thetaHistory: { at: number; theta: number }[];
  srsCards: Record<string, FsrsCard>;  // לפי Lexeme id
  attempts: Attempt[];
  remediationQueue: RemediationEntry[];
}

interface Attempt {
  questionId: string;
  chosenIndex: number;
  correct: boolean;
  elapsedMs: number;
  at: number;
  diagnosis: DiagnosisCause | null;   // null כשהתשובה נכונה
}

type DiagnosisCause =
  | 'vocabulary-gap'
  | 'distractor-phonetic'
  | 'connector-misread'
  | 'time-pressure'
  | 'inference-error';

interface RemediationEntry {
  cause: DiagnosisCause;
  targetId: string;         // Lexeme id, או trapType, לפי הסיבה
  createdAt: number;
  servings: number;         // כמה פעמים כבר הוגש בסשן
}
```

רשומת תיקון יוצאת מהתור לאחר שתי הגשות שנענו נכון, או לאחר 14 יום — המוקדם מביניהם. ללא פינוי, התור מצטבר ומשתלט על הסשנים.

## 6. המנועים

### 6.1 מנוע מיקום

רץ פעם אחת, בהפעלה הראשונה.

- 20 פריטים, חיפוש בינארי על ציר הקושי
- מתחיל ב-theta = 0; כל תשובה מזיזה את האומדן, גודל הצעד קטן עם ההתכנסות
- פלט: theta התחלתי + זריעת כרטיסיות SRS

**זריעת הכרטיסיות:** לכל `targetLexeme` שנפגש במבחן המיקום נוצרת כרטיסיית FSRS. מילים מתוך שאלות שנענו **נכון** נזרעות כ"נראתה" עם מועד חזרה רגיל. מילים מתוך שאלות שנענו **שגוי** נזרעות עם מועד חזרה מיידי ונכנסות לתור התיקון. מילים שלא נפגשו כלל נשארות ללא כרטיסייה עד למפגש ראשון.

### 6.2 מיפוי theta לציון משוער

```
score = clamp(round(100 + theta * (50 / 3)), 50, 150)
```

theta של 0 → 100. theta של +2.04 → 134 (סף הפטור). theta של +3 → 150.

**הסתייגות מפורשת:** זהו אומדן פנימי, **לא ציון מאל"ו**. הכיול הסטטיסטי האמיתי של מאל"ו אינו פומבי. המספר שימושי למעקב אחרי **מגמה** — עולה, תקוע, יורד — ולא כתחזית מדויקת לציון בבחינה. האפליקציה תציג את ההסתייגות הזו במסך ההתקדמות, לא רק במסמך.

### 6.3 מנוע חזרות מרווחות

**FSRS** על הפריטים הלקסיקליים. אלגוריתם מוכר ופתור, ללא המצאות.

כרטיסייה נחשבת "נשלטת" כשמרווח החזרה שלה עולה על 21 יום.

### 6.4 מנוע האבחון

הליבה של גישה B. כל תשובה שגויה מסווגת לסיבה אחת, **לפי סדר הבדיקות הבא**:

| # | בדיקה | סיווג | תרופה |
|---|---|---|---|
| 1 | קיים `targetLexeme` שאינו נשלט ב-SRS | `vocabulary-gap` | המילים נכנסות לתור SRS בעדיפות מוגברת |
| 2 | האפשרות שנבחרה מופיעה ב-`confusableWith` של הנכונה | `distractor-phonetic` | תרגול זוגות מבלבלים זה מול זה |
| 3 | `trapType` של השאלה הוא `logic-inversion` | `connector-misread` | דריל ממוקד במילות קישור |
| 4 | `elapsedMs` מעל אחוזון 90 האישי לסוג השאלה | `time-pressure` | אותו סוג שאלה תחת שעון לוחץ יותר |
| 5 | ברירת מחדל | `inference-error` | הבנת הנקרא מונחית |

**הסדר אינו שרירותי.** אם המשתמש אינו יודע את המילה, כל שאר הסיווגים הם תסמין ולא סיבה. בדיקת פער אוצר המילים חייבת להיות ראשונה.

שתי הבהרות תפעוליות:

- **בדיקה 1** — מילה שאין לה כרטיסיית FSRS כלל נחשבת "אינה נשלטת". אי-מפגש הוא מקרה פרטי של פער.
- **בדיקה 4** — אחוזון 90 האישי מחושב רק משהצטברו לפחות 20 ניסיונות באותו סוג שאלה. עד אז משמש סף קבוע: פי 1.5 מהזמן המוקצב לשאלה בבחינה האמיתית (למשל 90 שניות להשלמת משפטים).

### 6.5 בונה הסשן

קלט: מספר דקות פנויות (המשתמש בוחר). פלט: רשימת פריטים לסשן.

סדר עדיפויות:

1. **כרטיסיות SRS שהגיע זמנן** — זולות בזמן, ערך גבוה
2. **תור התיקון** מטעויות אחרונות
3. **חומר חדש ב-theta + 0.5** — מעל רמת הנוחות, בכוונה
4. מילוי עד תקציב הזמן

אומדני זמן לתכנון הסשן:

| סוג פריט | אומדן |
|---|---|
| כרטיסיית SRS | 8 שניות |
| השלמת משפטים | 60 שניות |
| דקדוק בהקשר | 60 שניות |
| ניסוח מחדש | 120 שניות |
| קטע קריאה + 5 שאלות | 900 שניות |

קטע קריאה הוא **פריט אטומי** — נכנס לסשן רק אם נותרו לפחות 900 שניות בתקציב. אין הגשת חצי קטע.

סעיף 3 מיישם את מסקנה 2 מסעיף 1.1: בלי מפגש עם קושי גבוה אין ציון גבוה, גם בדיוק מושלם.

### 6.6 כיול אמפירי מחדש

דירוגי הקושי ההתחלתיים הם הערכה ידנית ולכן שגויים במידה מסוימת.

תיקון: האפליקציה מתעדת ביצועים בפועל לכל פריט. משהצטברו לפחות 8 ניסיונות, הקושי האפקטיבי מחושב כך:

```
observed             = thetaMean - logit(pCorrect)
difficultyEffective  = (8 * authored + n * observed) / (8 + n)
```

- `n` — מספר הניסיונות שנצברו על הפריט
- `pCorrect` — שיעור התשובות הנכונות, חסום לטווח `[0.05, 0.95]` כדי למנוע התבדרות ב-logit
- `thetaMean` — ממוצע ה-theta של המשתמש בזמן אותם ניסיונות

זהו אומדן קושי בסגנון Rasch: פריט שנענה נכון לעיתים רחוקות ברמת theta נתונה הוא פריט קשה. ככל שנצברים נתונים, המשקל עובר מההערכה הידנית שלי לנתונים בפועל.

**הערה על משתמש יחיד:** עם נבחן אחד, `observed` משקף גם את החולשות הספציפיות שלו ולא רק את קושי הפריט. זו הטיה מקובלת כאן — האפליקציה משרתת אותו בלבד, ולכן כיול לפיו הוא התנהגות רצויה ולא באג.

## 8. מה נמצא מחוץ לתחום

**פרקי הפיילוט אינם נבנים**, למעט אחד:

| פרק פיילוט | החלטה | נימוק |
|---|---|---|
| השלמת קטע שמע | לא | דורש תשתית אודיו. תשואה: חלק מ-2 נקודות בונוס |
| הבנת הנשמע | לא | כנ"ל |
| מטלת כתיבה | לא | דורש ניקוד חיבורים — בלתי אפשרי בלי LLM, והוגדר שאין מפתח API |
| יצירת מילה | לא | תשואה נמוכה ביחס לעלות |
| **דקדוק בהקשר** | **כן** | זול לבנות, ומחזק תחביר שמשרת גם את פרקי ניסוח מחדש |

הנימוק הכולל: פרקי הפיילוט שווים **עד 2 נקודות בונוס**. אותו מאמץ מושקע באוצר מילים מניב יותר.

כמו כן מחוץ לתחום: ריבוי משתמשים, סנכרון בין מכשירים, אפליקציית מובייל, פריסה לאינטרנט, יצירת תוכן בזמן ריצה.

## 9. תוכנית התוכן

### 9.1 יעד סופי

| סוג | כמות |
|---|---|
| פריטים לקסיקליים | ~600 (570 משפחות AWL + מילות קישור + תחיליות/סיומות) |
| השלמת משפטים | ~300 |
| ניסוח מחדש | ~150 |
| קטעי קריאה | ~25 (125 שאלות) |
| דקדוק בהקשר | ~60 |

### 9.2 העלות האמיתית

**כתיבת המאגר, לא כתיבת הקוד, היא נתח העבודה הגדול.** כל פריט דורש תיוג ידני נכון: רמת קושי, `targetLexemes`, `trapType`, והסבר לכל אחת מארבע האפשרויות.

לכן התוכן נבנה **בגלים**, והאפליקציה שמישה מהגל הראשון.

### 9.3 גלים

**גל 1 — סף שמישות.** מאפשר מבחן מיקום וכ-10 ימי לימוד:

- 150 פריטים לקסיקליים (AWL תת-רשימות 1–3, התדירות הגבוהה ביותר)
- 40 מילות קישור
- 60 השלמת משפטים
- 30 ניסוח מחדש
- 6 קטעי קריאה (30 שאלות)

**גלים 2–3 — הרחבה מונחית-אבחון.** נכתבים בזמן שהמשתמש כבר לומד, **ומכוונים לחולשות שהאבחון חשף בפועל** במקום לניחוש מראש. זהו יתרון של המבנה בגלים, לא פשרה.

## 10. כיוון עיצובי

**שוויצרי/בינלאומי.** מינימליזם ספציפי — היררכיה טיפוגרפית חדה, רשת נקייה, צבע רק כשהוא נושא משמעות. לא "אפור על לבן עם צבע הדגשה דקורטיבי".

הנימוק אינו אסתטי בלבד: זהו מסך שבוהים בו בסשנים ארוכים. רעש ויזואלי גובה מס קשב שנחוץ למשימה עצמה.

### 10.1 טיפוגרפיה

התוכן של האפליקציה *הוא* טקסט אנגלי אקדמי הנקרא תחת לחץ זמן. לכן:

- רוחב שורה ~65 תווים
- ריווח שורות נדיב
- גופן בעל קריאות אמיתית בגדלים קטנים

מהירות הקריאה היא אחד הדברים שהבחינה מודדת. הטיפוגרפיה כאן פונקציונלית.

### 10.2 דו-כיווניות (bidi)

ממשק בעברית (RTL) ותוכן באנגלית (LTR) על אותו מסך.

**כל בלוק טקסט אנגלי מקבל `dir="ltr"` ו-`unicode-bidi: isolate`.** בלי זה, משפט כמו `The results were inconclusive, despite the researcher's claims.` נשבר: הנקודה קופצת לתחילת השורה והגרשים מתהפכים.

זהו פרט תקינות, לא פרט אסתטי. שאלה שמוצגת שבורה היא שאלה פסולה.

### 10.3 צבע

צבע סמנטי בלבד:

- ירוק — נכון
- אדום — שגוי
- ענבר — ממתין לחזרה / אזהרת זמן

אין צבע דקורטיבי, אין גרדיאנטים. כשכל השאר אכרומטי, הצבע היחיד על המסך נקרא מיד.

**בהיר כברירת מחדל.** מצב כהה קיים כאופציה.

### 10.4 השעון

**קו התקדמות דק, לא ספרות רצות.**

ספרות יורדות מייצרות חרדה ומושכות מבט כל שנייה — קשב שנגזל מהשאלה. קו שמתקצר נקלט בראייה היקפית.

מתחת ל-20% מהזמן שנותר הקו הופך לענבר. זו ההתראה היחידה.

### 10.5 טוקנים

כל ערכי הצבע, הטיפוגרפיה והמרווחים מוגדרים כמשתני CSS ב-`tokens.css`. אין ערכים קשיחים חוזרים בקומפוננטות.

## 11. בדיקות

ארבעה מודולים מקבלים כיסוי יוניט מלא:

1. **חישוב theta** — עדכון אומדן, התכנסות, מיפוי לציון
2. **תזמון FSRS** — מרווחים, מעברי מצב, סף שליטה
3. **מסווג האבחון** — כל אחד מחמשת הסיווגים, כולל סדר הקדימות
4. **בונה הסשן** — עמידה בתקציב זמן, סדר עדיפויות, בחירת קושי

**נימוק:** באג באזורים האלה אינו קורס. הוא משקר בשקט על ההתקדמות במשך שבועות, ומתגלה רק בבחינה עצמה. זהו סוג הכשל המסוכן בפרויקט הזה.

בדיקות אינטגרציה: זרימת סשן מלאה, שמירת מצב ושחזורו, נעילת פרק בסימולציה.

בדיקות ויזואליות אינן בהיקף — משתמש יחיד, מסך יחיד.
